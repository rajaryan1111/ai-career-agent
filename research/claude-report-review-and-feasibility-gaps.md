# Claude Research Review: Findings, Corrections, and Feasibility Gaps

**Date reviewed:** 2026-10-13  
**Status:** Research only. No implementation authorized.  
**Input:** A partial research report from Claude supplied by the project owner.  
**Important:** This document is a critical review, not an endorsement of every claim in the supplied report. It separates independently checked facts from hypotheses and unresolved claims.

## Executive conclusion

The strongest direction remains a local-first, quality-first job-search workspace built around verified candidate facts, hard eligibility checks, application preparation, evidence-backed tracking, and source-specific permitted discovery.

The report's most useful strategic recommendation is to defer automated submission from the first release. However, the claim that the competition is weakest at application submission is not yet supported by adequate hands-on competitor research. Likewise, a Greenhouse/Lever/Ashby plus Adzuna discovery strategy is a hypothesis, not a proven zero-cost solution.

## What to retain as strong hypotheses

1. **Evidence-backed candidate facts:** generated application materials should map to user-confirmed facts or be flagged for review.
2. **Hard eligibility gates:** mandatory qualifications should not be outweighed by a high keyword score.
3. **Application kit with a diff:** show what changed from the master resume and keep the original intact.
4. **Application ledger:** distinguish prepared, opened, user-submitted, and confirmed states; retain source and evidence.
5. **Catch-up digest:** if the computer was asleep/offline during a scheduled search, catch up when the app next runs rather than promising impossible background execution.
6. **Narrow initial audience:** test final-year students and recent graduates first as a hypothesis, rather than building for everyone immediately.
7. **Defer auto-submit:** keep submission out of the initial scope until specific workflows are proven permitted, safe, and reliable.

These remain proposals until validated with users and tests.

## Independent source checks

### LinkedIn automation restriction — high confidence for the stated rule

LinkedIn's official help page says it does not permit third-party software, crawlers, bots, plugins, or extensions that scrape, modify the appearance of, or automate activity on its website. It warns that use may lead to account restrictions.

Source: https://www.linkedin.com/help/linkedin/answer/a1341387/prohibition-of-scraping-software?lang=en  
Also checked: https://www.linkedin.com/help/linkedin/answer/a1341543

**Implication:** Do not plan a LinkedIn scraping or interaction automation adapter without an explicitly permitted official integration or written permission. Any user-directed import or linking behavior still needs a separate terms review.

### Indeed automated applications — high confidence for the stated rule

Indeed's official India job-seeker guidance says not to use third-party bots or automated tools to apply for jobs. It also warns that using web forms on its services is not allowed.

Source: https://support.indeed.com/hc/en-in/articles/360028540531-Indeed-Jobseeker-Guidelines

**Implication:** Do not automate application actions on Indeed absent explicit authorization. Treat discovery, opening links, application preparation, and application submission as separate capabilities.

### Lever postings API — high confidence that both read and programmatic apply endpoints exist; permission for our product is not established

Lever's official API documentation says its postings API can list and retrieve a company's public job postings and can programmatically apply. The documented application endpoint requires an API key generated by a Super Admin of the employer's Lever account. The API is designed for creating a company's job site, and the documentation recommends using Lever's hosted form if a custom form cannot handle rate limits and errors.

Source: https://github.com/lever/postings-api

**Important correction to oversimplified conclusions:** the API technically has an apply endpoint, but an ordinary job seeker cannot assume they can obtain an employer-issued key or that this authorizes a general-purpose third-party application agent. Treat it as unavailable for generic applicant-side submission unless an authorized integration is established.

### Ashby public job postings API — high confidence for employer-board retrieval, not global search or third-party submission

Ashby's official documentation describes a public job postings API for a specific organization's job board, including job title, location, description, employment type, published date, and application URL where supplied.

Source: https://developers.ashbyhq.com/docs/public-job-posting-api

A separate API reference notes that unlisted postings should not be displayed publicly unless the API is called with listed-only filtering.

Source: https://developers.ashbyhq.com/reference/jobpostinglist

**Implication:** A public endpoint can be a useful company-board connector, but it is not evidence of a universal cross-company job-search API or permission to submit applications through Ashby.

### Greenhouse — additional verification required

Official developer resources confirm that Greenhouse has a Job Board API and other recruiting APIs. The source page also announces that Harvest v1/v2 were deprecated on August 31, 2026; avoid relying on stale API assumptions.

Source: https://developers.greenhouse.io/

The precise claim that every relevant job-board read endpoint is unauthenticated and that application submission always requires an employer-issued key was not fully verified in this review. Verify the current Job Board API documentation before recording those details as final.

### Adzuna — not yet verified enough to use as a core dependency

The supplied report cites conflicting quotas from secondary sources. No quota or usage-limit claim should be treated as settled until verified against Adzuna's current official API documentation and terms.

**Implication:** Do not make Adzuna essential to the MVP until coverage, quota, retention, attribution, permitted use, and costs are documented.

## Important corrections and caveats in the supplied report

1. **The repository 404 is not proof that the repository is missing or renamed.** The repo is private. An unauthenticated public lookup can return 404 for a private repository. The project owner has an authenticated GitHub connection that can access it.
2. **“The competition is weakest at application submission” is unproven.** The report did not test products hands-on and used competitor or third-party sources for some claims. Keep it as a research question, not a finding.
3. **Competitor prices and complaints need better evidence.** Rival comparison pages and review aggregators can be biased or outdated. Use current vendor pricing pages and balanced user reports; capture date, plan, and geography.
4. **“Company ATS boards are legitimate and free” needs nuance.** Public read access may be free, but source coverage, API terms, company-board discovery, rate limits, data reuse, refresh costs, and maintenance all matter.
5. **ATS public APIs are generally board-specific.** An endpoint for one company's job board does not automatically solve how to discover all employers using that ATS.
6. **A pasted-link fallback is promising but incomplete.** It needs a reliable way to extract job details without violating source restrictions, handle pages requiring login, identify expired listings, and avoid accidentally storing sensitive content.
7. **Do not infer a scam from a single weak signal.** Show sourced risk indicators, confidence, and uncertainty; allow the user to inspect the evidence.

## Updated feature priorities to investigate

### P0 — validate first
- Candidate fact vault with provenance, confirmation, and freshness.
- Mandatory eligibility filters with visible reasons.
- Source and last-checked timestamp for every listing.
- Deduplication and expired-listing checks.
- Role-specific application kit and visible resume diff.
- Application ledger with explicit evidence and status semantics.
- User-controlled local storage, export, and deletion.
- Source capability registry separating discovery, detail retrieval, autofill, and submission.

### P1 — test after core workflow
- Company verification report with official-domain checks and evidence.
- Internship-specific fields for stipend, duration, year/branch eligibility, and location.
- Catch-up digest after sleep/offline periods.
- Interview prep grounded in the actual job description and verified candidate history.
- Outcome analytics that warn about small sample sizes.

### Defer
- Automatic submission on major job boards until explicitly permitted and tested.
- Bulk applying or mass recruiter outreach.
- Any CAPTCHA/OTP/access-control bypass.
- Unverified scam scoring presented as fact.
- Universal platform coverage claims.
- Any mandatory paid AI provider or cloud account.

## Next research steps in order

1. Complete the official terms/API matrix for Naukri, Internshala, Wellfound, Workday, Greenhouse, Lever, Ashby, and Adzuna.
2. Validate company-board coverage: how would we discover enough relevant company boards without scraping a prohibited source?
3. Test at least two competitors hands-on using one internship and one entry-level role; record actual time, errors, manual work, and data handling.
4. Interview 10–15 target users about their actual sources, application pain points, and willingness to use a desktop app.
5. Create a human-labeled set of 100–200 jobs and measure eligibility and top-result precision.
6. Test local resume extraction and application-kit quality on the target MacBook hardware, with user-confirmed ground truth.
7. Measure time saved versus a manual application and check that tailoring never adds unsupported facts.
8. Review applicable privacy and data-protection obligations before selecting a storage/AI design.

## Decision gate before implementation

Do not begin implementation until we have:
- At least three useful discovery sources with documented permitted access and coverage evidence.
- A validated initial user segment and demonstrated workflow pain.
- A measured job-relevance baseline and resume/application-quality test plan.
- A feasible privacy and zero-mandatory-cost design.
- At least one permitted end-to-end workflow, with clear evidence for submission status.
- A clear scope excluding unverified platform automation.
