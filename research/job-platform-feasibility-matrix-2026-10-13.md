# Job Platform Feasibility Matrix — Official-Source Review

**Checked:** 2026-10-13  
**Status:** Research only; no implementation authorized.  
**Scope:** Candidate-side job discovery and application preparation for a local-first desktop agent with a ₹0 initial budget. This is a product-feasibility assessment, not legal advice. Platform terms can vary by country, logged-in state, employer configuration, and subsequent policy changes.

## Executive decision

**Do not build a universal scraper or auto-apply bot.**

The reproducible pre-implementation acceptance checks are now specified in [Source Validation Test Suite](source-validation-test-suite-2026-10-13.md). The current seed CSV passes its structural check (55 mixed records, 27 columns per row, unique IDs), but the live-source coverage gate has not passed. The currently verified path is a set of source-specific connectors to public employer job boards, plus a user-provided job URL workflow. These are separate capabilities and must be evaluated independently:

1. Discover a listing.
2. Retrieve details and the description.
3. Prepare materials locally.
4. Autofill a form.
5. Submit an application.
6. Verify submission.

A public listing or technically reachable API is not blanket permission for every downstream use. For the first release, keep final submission under the user's control and do not automate platforms whose published rules prohibit it or whose authorization is unclear.

## Verified official-source details

### Greenhouse

The current Job Board API documentation says public job-board data is available without authentication for GET endpoints. It documents:
- `GET /v1/boards/{board_token}/jobs` for listing jobs.
- `?content=true` to include descriptions and related details.
- A job-detail endpoint and optional application question metadata.
- An application POST endpoint that requires Basic Auth using a Job Board API key.

The same documentation cautions that a custom application flow needs validation for required fields and recommends the hosted form in many cases. The existence of the POST endpoint is not proof that a general-purpose candidate-side app can obtain credentials or is authorized to submit on a user's behalf.

Sources:
- https://docs.greenhouse.io/job-board.html
- https://support.greenhouse.io/hc/en-us/articles/10568627186203-Greenhouse-API-overview
- https://harvestdocs.greenhouse.io/ (current Harvest v3 documentation; do not rely on deprecated Harvest v1/v2, which Greenhouse says became unavailable after 2026-08-31)

**Implication:** Strong candidate for a controlled public-board discovery proof of concept, subject to checking current terms, rate limits, and data-use requirements. Submission remains out of scope.

### Lever

Lever's official postings API documents:
- Listing and retrieving published postings for a named company site.
- Job details including description and hosted apply URL.
- No global full-text search over all open jobs.
- A programmatic application POST endpoint, but it requires an API key generated by a Super Admin of the employer's Lever account.
- A 429 rate limit above two application POST requests per second for custom job sites.

Sources:
- https://github.com/lever/postings-api
- https://api.lever.co/v0/postings/leverdemo?mode=json (official example endpoint linked from Lever documentation)

**Implication:** Candidate-board discovery is technically promising but company-board enumeration is an unresolved product problem. Do not treat the employer-key application endpoint as available to an ordinary applicant.

### AI Dev Jobs

The official API docs describe anonymous public read endpoints for job search and detail retrieval, with filters for role level, location, workplace and explicit worldwide remote scope. Its terms, updated 2026-04-16, say API data may be used in applications but may not be resold as a standalone dataset; they prohibit scraping beyond API rate limits. The provider disclaims listing accuracy, completeness and availability. This is a meaningful fit for an AI/ML-focused discovery experiment, but does not establish coverage for Indian internships/fresher roles.

**Implication:** Highest-priority source for a small, human-reviewed coverage test because the documented access and application-use language is clearer than several alternatives. It is not yet production-approved: measure target-role coverage, freshness, direct links, duplicates, eligibility fields and false positives; use the official API only within its throttles; retain minimal fields and link to the original employer listing. Treat its own match scores as non-authoritative and apply our own eligibility rules. Do not use the provider's application endpoint as a generic external job-submission mechanism.

Sources:
- https://aidevboard.com/docs
- https://aidevboard.com/terms
- https://aidevboard.com/privacy

**Live smoke-test update (2026-10-13):** The official endpoint returned structured job records and pagination metadata, but the first visible records were senior roles. The documented job-type enum does not include internship. This does not prove India/junior queries are empty; target coverage remains unmeasured. See [live smoke test](live-source-smoke-test-2026-10-13.md).

### Remote OK

Remote OK's official FAQ says its JSON and RSS feeds are free and unauthenticated, and specifically asks aggregators to credit Remote OK and link to each original job post. Its current terms (updated 2026-07-20) additionally require a web or in-app hyperlink back to Remote OK on the screen/page where API/site data is used.

**Implication:** A viable candidate for a remote-only coverage test if the app can satisfy attribution visibly on the relevant screen and link each role to its original listing. Do not infer “remote” means worldwide eligibility. Current rate limits, caching/retention details, India-candidate eligibility, stale-listing rates and target-role coverage still need measurement; do not integrate before those checks.

Sources:
- https://remoteok.com/api
- https://remoteok.com/remote-jobs.rss
- https://remoteok.com/faq
- https://remoteok.com/legal

**Live smoke-test update (2026-10-13):** The feed returned structured JSON with a legal/attribution record and job records. Visible entries included non-target functions, and a remote India listing was not an entry-level AI example. This is only a few visible records; relevance and India fresher coverage remain unmeasured. See [live smoke test](live-source-smoke-test-2026-10-13.md).

### Ashby

Ashby's public job-posting API retrieves currently published postings for a named organization job board. The response can include title, location, description, work arrangement, employment type, publication date, and job/apply URLs. Its separate authenticated `jobPosting.list` API explicitly warns that unlisted postings should not be publicly displayed unless `listedOnly=true` is used, and it requires `jobsRead` permission.

Sources:
- https://developers.ashbyhq.com/docs/public-job-posting-api
- https://developers.ashbyhq.com/reference/jobpostinglist
- https://developers.ashbyhq.com/reference/jobpostinginfo

**Implication:** Use only the documented public board endpoint for public discovery; do not expose unlisted postings or infer a global job search API from the board-specific endpoint.

### SmartRecruiters

The official Posting API documents list/detail endpoints for postings associated with a named employer board. The API platform page points to the SAP API Policy, which restricts autonomous/generative-AI API-call orchestration and systematic extraction unless the relevant endorsed pathway or authorization applies. Credentials can also expose internal postings if configured with the relevant permission, so a distributed app must not assume anonymous/public-only access or use broadly privileged credentials.

**Product stance: not approved pending explicit written authorization or confirmation of an applicable endorsed pathway.** Do not run a broad coverage test, build an adapter, or count it as a permitted source before this is resolved. See [dedicated review](smartrecruiters-api-policy-review-2026-10-13.md).

Sources:
- https://developers.smartrecruiters.com/docs/posting-api
- https://developers.smartrecruiters.com/docs/endpoints
- https://developers.smartrecruiters.com/docs/the-smartrecruiters-platform
- https://help.sap.com/doc/sap-api-policy/latest/en-US/API_Policy_latest.pdf
- https://developers.smartrecruiters.com/docs/permission-reference

### Adzuna

The official API documents a job-search endpoint and default access limits:
- 25 hits/minute
- 250 hits/day
- 1,000 hits/week
- 2,500 hits/month

The terms state that limits may change and that Adzuna has discretion over access. They list publishing Adzuna listings, publishing Jobsworth salary estimates, and personal research as permissible uses. They also say other uses by commercial, government, or academic organizations (including affiliates or individuals) are subject to a 14-day trial period for validation of coverage, quality, and usability.

Sources:
- https://developer.adzuna.com/docs/search
- https://developer.adzuna.com/docs/terms_of_service
- https://developer.adzuna.com/activedocs

**Implication:** This is not a guaranteed permanent, unlimited, zero-cost production source. Before adoption, confirm that the intended use (especially a distributed desktop product) fits the current terms; test Indian coverage and deduplication; document attribution, caching/retention, and credential handling.

### LinkedIn

LinkedIn's official help says third-party software, crawlers, bots, plugins, and extensions that scrape, modify the appearance of, or automate activity on the site are not permitted and may lead to account restrictions.

Sources:
- https://www.linkedin.com/help/linkedin/answer/a1341387/prohibition-of-scraping-software?lang=en
- https://www.linkedin.com/help/linkedin/answer/a1341543

**Implication:** Exclude LinkedIn scraping and automated interactions from the design. Do not try to evade detection or access controls.

### Indeed

Indeed's official India jobseeker guidance says not to use third-party bots or other automated tools to apply for jobs. It also says use of web forms on Indeed's platform/program/service is not allowed and may result in interrupted or blocked access.

Source:
- https://support.indeed.com/hc/en-in/articles/360028540531-Indeed-Jobseeker-Guidelines

**Implication:** No application automation on Indeed. Do not assume discovery automation is permitted merely because the explicit wording above focuses on applying; any separate access method still needs terms review.

### Wellfound

Wellfound's official Talent General Terms prohibit copying/distributing content except as expressly permitted, including through automated or non-automated harvesting, collection, or scraping. The terms also restrict automated systems that impose more load than a human browser and competitive use of site content.

Source:
- https://wellfound.com/terms

**Implication:** No scraping or bulk listing collection without an authorized basis. A human-visible user workflow does not automatically authorize automated extraction.

### Workday

Workday's official online terms, last updated 2026-08-13, prohibit data mining, robots, or similar data-gathering methods designed to scrape/extract site data, and prohibit applications that interact with its sites without prior written consent. The terms also say Workday APIs require authorization under a separate agreement.

Source:
- https://www.workday.com/en-us/legal/site-terms.html

**Implication:** Do not create a generic Workday scraper or form-submission bot. Employer-specific career tenants and authorized integrations need separate assessment; a job page being public does not negate the platform terms.

### Naukri and Internshala

This pass did not obtain enough verifiable official documentation to state their current automation terms, public APIs, feed availability, quotas, or permitted application behavior. Search snippets and third-party commentary are not sufficient to fill this gap.

**Implication:** Keep them as unresolved research items, not assumed integrations. Before testing any automated access, capture the current official terms and identify an official API/feed or written authorization. Manual user navigation can remain an optional user workflow, but do not silently automate it.

## Strategic consequence: the hard part is board discovery, not just parsing

Greenhouse, Lever, and Ashby each expose job data at the employer-board level. None of these findings establishes a universal, comprehensive cross-employer search endpoint. Even if each connector is free and technically accessible, the product still needs a lawful, maintainable way to discover company board names and keep the list fresh.

Do not solve this by quietly scraping LinkedIn, Indeed, Wellfound, or Workday. Candidate approaches to test:
1. A curated, user-editable company list with official careers-page links.
2. Public employer career pages that link to a known ATS board, discovered through permitted search/index mechanisms and then checked against the source's terms.
3. User-pasted job/company URLs.
4. Adzuna only if its current terms explicitly support the intended distributed-product use and coverage proves useful.
5. An opt-in community-maintained list of company board URLs, with provenance and last-verified timestamps.

Each is a hypothesis until tested for coverage, freshness, and maintenance burden.

## Recommended capability policy for the product

| Capability | Initial stance |
|---|---|
| Retrieve jobs from documented public employer-board endpoints | Allow only after source-specific terms and usage conditions are reviewed |
| Retrieve details from pages that require login or block automated access | Do not bypass access controls; request user input or leave unsupported |
| Rank and filter locally using user-confirmed facts | Allow; explain every hard rejection and score |
| Generate resume/cover-letter variants | Allow only from verified candidate facts; show a diff and flag uncertain claims |
| Autofill forms | Defer; enable only on specifically reviewed, permitted workflows and require user review |
| Submit applications | Out of initial scope; require explicit per-source authorization, reliable error handling, and user confirmation |
| CAPTCHA, OTP, anti-bot, or access-control bypass | Never implement |
| Mark submission as complete | Only after user confirmation or strong source evidence; otherwise label “prepared”, “opened”, or “user says submitted” |
| Reuse or retain job data | Store source URL, timestamp, and minimal necessary fields; check source-specific reuse/retention terms first |

5. **ATS proof of concept only after the above:** test a small set of Greenhouse, Lever, and Ashby public boards for duplicate handling, stale listings, description extraction, remote/location normalization, and missing eligibility data.
6. **User validation:** interview 10–15 students/recent graduates about which sources they actually use, which jobs are missed by company boards, and whether a curated source list would be valuable.

- Do AI Dev Jobs and Remote OK produce enough current, relevant India/international-fresher listings to meet quality thresholds after human review?
- Does Adzuna authorize the exact distributed desktop use case and what attribution/cache rules apply?
- Can SmartRecruiters/SAP confirm in writing that this AI-agent use is allowed, and identify the required endorsed architecture or authorization?
- What are the current official Naukri and Internshala access/automation rules?
- How much coverage do Greenhouse, Lever, and Ashby provide in the target Indian fresher/internship segment?

- What is the maintenance cost of a company-board registry if the monetary budget is ₹0?
